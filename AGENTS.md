# AGENTS.md — RenderScale (Stonecutter multiloader MC mod)

## What this is
Single-source Fabric / NeoForge / Forge mod built with Stonecutter 0.9.2 + Loom/ModDev. `src/main` is the ONLY hand-edited source; per-version projects under `versions/<mc>-<loader>/` contain only generated build output — never edit them.

## Stonecutter rules (easy to break)
- Version/loader conditionals use `//?` comments, e.g. `//? >=1.21.11 {`, `//? fabric {`, `//?} neoforge {`, `//? >26.1 { ... //?} else {`. Both branches must stay compilable.
- Mechanical renames live in `replacements.string(...)` blocks in `build.fabric-m/o.gradle.kts`, `build.neoforge.gradle.kts`, `build.forge.gradle.kts` (e.g. `ResourceLocation`↔`Identifier` for `>=1.21.11`, `FabricDataOutput`→`FabricPackOutput` for `>=26.1.2`). Don't rename these by hand in source.
- Template swaps/constants are defined in `stonecutter.gradle.kts` `stonecutter parameters` (`mod_version`, `mod_id`, `minecraft`, `iris`, `sodium`). Reference them; don't hardcode per-loader values.
- Common code (`RenderScale.java`) must stay loader-agnostic. Loader specifics go in `platform/{fabric,neoforge,forge}/` with entrypoints `FabricClientEntrypoint`, `NeoforgeClientEntrypoint`, `ForgeEntrypoint`.

## Version matrix gotcha
- `settings.gradle.kts` is TEMPORARILY trimmed to `match("26.2", "fabric", "neoforge")` for fast configuration; full matrix is commented out. Do not "restore" it unless the task needs another MC version. `vcsVersion = "26.2-fabric"`.
- `.sc_active_version` (`26.2-fabric`) is managed by Stonecutter and blocked by pre-commit (`scripts/prevent-protected-files-change.sh`). Never commit changes to it; reset to the VCS version before committing.
- Deps and compat ranges live in `stonecutter.properties.toml` (`deps.*`, `publish.additionalVersions`), not in build files.
- Java is per-MC in `build-logic/.../Context.kt`: MC `>=26` → 25, `>=1.20.6` → 21, older lower. Foojay provisions toolchains; CI builds with MS JDK 25. Use matching JDK when switching versions.
- Access mappings are per-MC in `src/main/resources/aw/` (`.accesswidener` for Fabric, `.cfg` for Forge/NeoForge, wired in each `build.*.gradle.kts`). Add both sides when exposing new members.

## Commands (Windows: use `gradlew.bat`)
- Full build (what CI runs): `./gradlew buildAndCollect --no-daemon` → jars land in `build/libs/<baseVersion>/`.
- Run game for active version: `./gradlew runActiveClient` (wrapper around `<active>:runClient`). Target a specific version: `./gradlew 26.2-fabric:runClient`.
- Per-MC publish wrappers (`stonecutter.gradle.kts`): `./gradlew publish<mcVersion>` → delegates to `publishMods`. Real publishing needs `.env` (copy `.env.template`; `MOD_IS_RELEASE`, `PUB_*` tokens) — never commit `.env`.
- No test/lint/typecheck suites exist; `buildAndCollect` is the verification step.

## Release / changelog
- Release tag must exactly equal `mod.version` + `mod.channel_tag` from `stonecutter.properties.toml` (`release.yml` deletes the tag+release on mismatch).
- Changelog is generated by git-cliff from conventional commits (`cliff.toml`); write commits as `feat:`/`fix:` etc.

## Misc
- Bump `Constants.BUILD_TAG` on each test build so logs/screenshots self-identify.
- Publishing metadata (mod id `renderscale`, incompatibilities with `resolutioncontrol*`, cloth-config/iris/sodium ranges) is generated by `build-logic` (`ModPlatformPlugin.kt`) — edit properties/build files, not generated manifests.
